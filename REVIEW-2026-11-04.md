## 1. Measured vs hypothesis

### Measured (Pixel logs in `benchmarks/2026-11-03-vulkan-ab/`)
- **Memory.** `memory.csv`: with the heap import (`unit_scale_1`), PSS is ~3.82–3.89 GB from t=10 s on. With
  `LARECOMP_VK_NO_GMEM=1` it starts ~1.1 GB and climbs to 2.81 GB at 300 s; native heap rises 9.6 MB -> 672 MB,
  ~2.2 MB/s after t=80 s. `bounded-run.csv`: PSS flat at 2.02–2.05 GB from 15 s to 120 s. Different scenes and
  lengths: the no_gmem climb is not yet shown to be a leak (a same-scene run past 120 s with the bounded build would
  settle it). The `swap_pss_kb` column reads `TOTAL` in every row: the capture script's column parse is off.
- **Frame time, presenting thread** (`bounded-run.log`, `[pace]`, medians):

  | t | period | blocked | busy |
  |---|---|---|---|
  | 0–60 s | 27.8 ms | 10.0 | 18.0 |
  | 60–120 s | 70.8 ms | 36.3 | 34.3 |
  | 120–180 s | 79.9 ms | 43.0 | 36.6 |

  Frames over 100 ms are not logged by `vk_pace_frame` (~9% of frames at 120–180 s), so these medians understate.
- **CPU** (`[cpumod]`, ITIMER_PROF, 10 ms of process CPU per sample): 2.78–2.85 cores in every 15 s window,
  menu (30–47 fps) and heavy scene (12 fps) alike. Shares: libc 29–33%, unclassified 24–27%, SDL3 22–25%,
  game 13–17%, runtime 3–5%, Vulkan/Mali 0–1%. One 8 KB SDL3 bucket (`0x1b2000`) takes ~370 samples per 15 s
  (~0.25 core) in every window.
- **Core stalls.** Every 2 s+ core-wait line in `bounded-run.log` is at start-up (log lines 121–234 of 3,587).
  Shorter waits are not logged, so the share of `blocked` that is core waiting is unknown (instrumented now, §3).

### Hypotheses (not established)
- CPU flat across scenes and fps suggests polling or spinning; the SDL3 bucket is the first candidate. Needs the
  symbol: `llvm-symbolizer --obj=<libSDL3.so from the APK> 0x1b2000 0x1b2800 0x1b3000 0x18c000 0xa0000`.
- libc's 30% may be the staging `memcpy` (§2), futex/condvar traffic, or `sched_yield` spins
  (`exec.c` pipeline jobs, `kernel.c` SleepThread(0)). The profiler did not print libc's bins until now (§3).
- The presenting thread's `blocked` time may be core waits (scheduler) or waits on other guest threads (game work).
  §3's split tells which.

## 2. Per-draw staging (`gfx_gmap`) correctness
- Semantics are unchanged from upstream: a storage buffer over `LARECOMP_GMAP_RANGE_MB` is dropped from the table, and
  a draw whose merged ranges exceed `LARECOMP_GMAP_TOTAL_MB` (or `GMAP_MAX` ranges) gets no table at all; shader
  global-memory reads in those cases return zero. That is the same failure mode upstream documents ("Buffers over
  8 MB, or more than 16 MB in all, are left out (their reads give zero, as before)"). Raising the limits only means
  fewer draws read zeros. The only correctness evidence for that path is rendering; the `[gmap] ... excluded` lines
  (first 12 each) say whether it happens at all.
- Cost: every staged draw copies its ranges on the CPU at draw time, now up to 32 MB per draw (was 16). No counter
  existed. Added: `[gmap] 2s: staged N draws, X MB copied in Y ms; left out R ranges, D draws` every 2 s.
- Note: the staged copy is a snapshot at draw-recording time. A buffer the CPU writes after the draw is recorded but
  before the GPU runs it is seen old; upstream accepts the same.

## 3. Instrumentation added (all log-only; nothing changes behaviour)
- `kernel.c`: per-thread `g_corewait_ns` (time in `core_acquire`, a subset of `g_blocked_ns`) and, per frame, the
  longest single core wait with its holder thread and that holder's last SVC.
- `exec.c` `vk_pace_frame`: `[pace] period P blocked B busy U ms core C` and, when a core wait over 1 ms occurred,
  `(longest L held by thread N svc S)`. Frames over 100 ms now log `[pace] hitch ...` with the same split. The old
  fields keep their order, so existing `period/blocked/busy` parsers still match.
- `exec.c` `gfx_gmap`: the 2 s staging counters above.
- `exec.c` CPU profiler (`LARECOMP_CPU_PROF=1`): libc hotspots are printed; each mapped object is listed once with
  its class, so the 24–27% unclassified bucket can be named.
- Verified on the review machine: desktop and Android-path syntax checks give the same diagnostics as before the
  change (one pre-existing ARM64-only `uc_mcontext.pc` error on an x86 check). `tools/test_sched` checks the
  accounting against the real `kernel.c`: in the sleep scenario the better thread's 1,355 ms blocked splits into its
  sleeps and 15 ms of core wait, holder = the worse thread.

## 4. Full `-O1` game-code build: feasibility and risks
- `-O1` is upstream's default and only tested setting: `Makefile` `GENFLAGS := -O1 -fno-strict-aliasing ...`, and the
  on-device builder `runtime/gamebuild.c` (`GAMELIB_CFLAGS`). The installed APK's `-O0` came from an override, so
  `-O0` is the untested configuration, not `-O1`.
- Compile time: upstream's generator already marks functions with a >16k-instruction switch `optnone`
  (`tools/gen.py` `HUGE_SWITCH_FN`; two dispatchers took 20+ minutes each at `-O1` before that). Expect a long
  build; PROGRESS.md notes compiler processes peaking near 3.2 GB of RAM, so cap parallel jobs to RAM.
- Expected gain is bounded by the measured share: game code is 13–17% of process CPU, so `-O1` cannot by itself
  close a 12 -> 30 fps gap. It matters more if that code is on the presenting thread's critical path, which §3's
  split plus a per-thread profile would show.
- `GENFLAGS` is hashed into `GAMELIB_ID`, so an `-O1` library gets a new id: runtime and game library must be
  rebuilt and shipped together.
